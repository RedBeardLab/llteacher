# LLTeacher initial AWS infrastructure decisions

**Status:** Accepted for the initial development stack

**Decision date:** 2026-07-07

**Stack:** `llteacher-dev` in `us-west-2`

## Context and goals

LLTeacher is transitioning from a legacy Django/SQLite application to a
TypeScript application backed by PostgreSQL. This phase establishes a small,
repeatable AWS foundation without moving existing data or coupling the new
application to the database prematurely.

The deliverables are one public application service, a container registry, a
private managed PostgreSQL database, and encrypted remote infrastructure
state. Django deployment, SQLite data transfer, production hardening, custom
domains, and CI/CD are explicitly deferred.

## Accepted decisions

### Pulumi with TypeScript

Pulumi uses the same primary language as the new application and permits
shared TypeScript tooling. Infrastructure lives in `infra/`, isolated from
runtime workspaces while remaining part of the npm workspace for dependency
locking and typechecking.

### App Runner and a single application container

AWS App Runner provides managed HTTPS ingress, health checks, deployment, and
scaling without an ECS control plane. One Node container serves both compiled
SPAs and the Hono API because the admin application is currently static and
does not justify a separate service.

The student app owns `/`, Hono owns `/api/*`, the admin SPA owns
`/instructor/*`, and `/health` is reserved for the platform health check.
`/legacy/*` is reserved for a possible later Django deployment and is not
implemented in this phase. The existing Cloudflare Worker entrypoint remains
available; the Node entrypoint is additive.

Images are stored in ECR with immutable Git-SHA tags. Automatic App Runner
deployments are disabled so promotion requires an explicit Pulumi update.
The service defaults to one instance, 1 vCPU, and 2 GB RAM, and may scale to
two instances at 50 concurrent requests per instance. Revisit this when load
tests or production traffic provide evidence for different limits.

### Private RDS PostgreSQL

RDS PostgreSQL 16 is provisioned in two isolated subnets across availability
zones. The development instance is single-AZ `db.t4g.micro` with 20 GB gp3
storage, storage autoscaling up to 100 GB, encryption, automated minor
upgrades, and seven days of backups. Development deletion protection is off
and deletion skips a final snapshot to keep iteration and teardown simple.
Production must reverse both deletion choices and evaluate Multi-AZ.

Credentials are generated by Pulumi and written to AWS Secrets Manager. Only
the secret ARN and non-secret endpoint metadata are exported. Passwords must
never appear in source, stack YAML, logs, or application environment files.

### Database intentionally disconnected

RDS is not publicly accessible and its security group has no ingress. The
application continues without `DATABASE_URL`; `/api/hello` therefore uses its
existing stub behavior. Django and SQLite remain outside App Runner because
App Runner has no persistent filesystem suitable for SQLite.

An App Runner VPC connector is deferred because attaching one sends
application egress through the VPC. WorkOS and OpenRouter require public
internet access, so safe database integration also requires NAT or another
deliberate egress design. The trigger to revisit this decision is the first
application feature that must read or write RDS.

### Network and state

The database VPC uses `10.42.0.0/16` and two isolated `/24` subnets. There is
no internet gateway, NAT gateway, bastion, or public database route in this
phase.

Pulumi state is stored in an account- and region-specific S3 bucket with
versioning, public access blocked, and KMS encryption. Pulumi secrets use the
same dedicated KMS key through the `awskms` secrets provider. The bootstrap
resources are created by an idempotent script because the state bucket and
KMS key must exist before Pulumi can manage the application stack.

## Known tradeoffs and revisit triggers

- App Runner favors operational simplicity over ECS-level networking and
  process control. Revisit if background workers, sidecars, or advanced load
  balancing become necessary.
- A single container couples student and admin releases. Split them when they
  need independent scaling, ownership, or release schedules.
- The generated App Runner URL is sufficient for development. Add DNS and a
  custom domain before external users depend on stable URLs.
- Local image publishing is intentionally manual. Add OIDC-based GitHub
  Actions after the deployment shape stabilizes.
- PostgreSQL is paid infrastructure while disconnected. Destroy the dev stack
  when it is not actively needed.
